## 2. Problem

Three holes exist today, and one of them cannot be closed without building something first.

1. **A manager or cs account is protected by a password only.** A Warehouse Manager is a near-admin on the server (`req_role`, `app.py:4145-4147`: a manager passes any admin route outside a short block list). `_twofa_required` returns true only when the *primary* role is `admin` (`app.py:764-770`). A worker with `extra_roles: ["admin"]` is not asked either (SEC-1).
2. **A badge scan alone opens a session for any account that holds a badge**, whatever its roles (`api_badge_login`, `app.py:12743-12780` — no role check, no second step, no `must_setup_2fa`). A badge is a printed card (SEC-2).
3. **Closing 2 today would lock people out.** A manager who signs in by badge would be sent to "password + code", and the only second step that exists is an authenticator app whose set-up routes refuse cs outright (`/api/2fa/*` are `@req_role("admin")`, `app.py:4957-5026`; a manager passes through the manager→admin rule, cs does not). Staff accounts have no email address (`api_add` writes `password, role, name, org` and optionally `extra_roles, allowed_channels, badge_token` — `app.py:12645-12653`).

So the order is forced: emailed codes first, proven with real inboxes, then the wider requirement, then the badge change.

## 6. Proposed behaviour

Numbers marked **(proposal)** are this spec's starting values. They are to be confirmed by the architect and security-reviewer and must be changeable without touching the app, because the app reads waits and counts from the server's answers.

### 6.1 Who is asked

- **Required:** effective roles (primary + `extra_roles`) contain admin, manager or cs — when the platform switch is on (§10). With the switch off, the rule is exactly today's (`role == "admin"`).
- **Enrolled accounts are always asked**, whatever the switch says and whatever their roles — as today (`app.py:4894`).
- **Never asked, never mailed:** any account of a sandbox company.
- Worker and host: no set-up offered in 1.0 (blueprint §3.2 puts optional two-step for them in 1.1). The set-up routes refuse an account that is neither required nor already enrolled.
- `twofa_exempt` on a user outside a sandbox company is ignored (SEC-3 — the sandbox PR's job; stated here so the two do not contradict).

### 6.2 Methods

An account has zero, one or two methods on: **email** (a confirmed address) and **authenticator** (today's `twofa_enabled`). "Enrolled" means at least one is on. A required account cannot turn off its last method. Both methods share one set of recovery codes.

If no mail transport is configured, or mail is suppressed (staging safe mode), **the email method is not offered at all** — at set-up or at sign-in. The server must not pretend a code was sent (today `_send_email` returns success in staging).

### 6.3 The code **(numbers are proposals)**

| Property | Value | Why |
|---|---|---|
| Form | 6 decimal digits, from the system's secure random source; shown in the email as `123 456` | matches the authenticator's 6 digits and the app's code field; six digits is the stated minimum in the guidance read (§11) |
| Lifetime | **10 minutes** from sending | same source: an emailed/out-of-band step is invalid unless completed within 10 minutes; long enough for a slow inbox |
| Single use | accepted once; a correct code is dead the moment it is accepted | |
| One live code | sending a new code cancels the previous one for that account and purpose | |
| Wrong tries per code | **5**, then that code is dead and a new one must be sent | a 6-digit code must not be guessable by repetition |
| Purpose-bound | a code sent for sign-in is not accepted for set-up, a change or deletion, and the other way round; a code is bound to the account, and at set-up also to the exact address it was sent to | |
| Storage | only a keyed, non-reversible form of the code, with its expiry, purpose and try count, **where every gunicorn worker reads the same value** (the shared database or a file under the existing cross-process lock — the architect chooses). Never process memory, never the session cookie | several workers; the cookie is readable by its holder |
| Logs | the code never appears in a log line, an error message, an audit entry, the email subject or a URL. The full address is not printed either (masked) | staging prints recipient and subject today |

### 6.4 Sending limits **(proposals)**

| Limit | Value | Counts |
|---|---|---|
| Wait before "Send again" | **30 s** after the first send of a step, **60 s** after each later one | per account + purpose |
| Per account | **5 sends per hour, 10 per rolling 24 hours** | all purposes together |
| Per destination address | **5 per hour, 10 per 24 hours** | protects a stranger's mailbox at set-up, where the address is typed |
| Per network (IP) | **30 sends per hour** | generous on purpose: the warehouse shares one public address |
| Whole platform | an alert to the platform owner at **200 code emails in 24 hours**; no automatic stop | catches a loop or abuse without locking the floor out |

A send that the server refuses for a limit is not counted. A send that timed out **is** counted, and its code stays valid (the email may still arrive).

Sending is only possible **after a correct password** (sign-in) or **inside a signed-in session** (set-up, change, deletion). Nobody can make the server email an account's address by knowing the username.

### 6.5 Checking limits **(proposals)**

| Limit | Value |
|---|---|
| Per account, any network | **10 wrong second-step answers in 15 minutes → the second step is locked for 15 minutes** for that account. Counts emailed codes, authenticator codes and recovery codes together. Sending a new code does **not** reset the count; only a correct answer does |
| Per account, long | **30 wrong answers in 24 hours → locked until the 24 hours pass or an admin resets the account's two-step** (audit entry, §6.10) |
| Per network (IP) | **40 wrong answers in 5 minutes** — the value the badge screen already uses for a shared address |
| Existing `ip|username:2fa` throttle | stays (8 in 5 minutes) |

These counters are reachable only by someone who already typed the correct password, so they cannot be used to lock out a manager by knowing a username. The per-account cap on the **password** step (the other half of SEC-11) can be used that way and is left to SEC-11's own PR.

### 6.6 Enrolment — adding and confirming the address

1. The person chooses Email, types an address, taps "Send code".
2. The server checks the shape of the address (one `@`, a dot in the domain, at most 254 characters, no spaces or control characters), lower-cases the domain, and sends a set-up code to it. The address is held as **pending**; it is not used for anything else.
3. The person types the code. Only now is the address stored as confirmed, the email method turned on, `must_setup_2fa` cleared, and — if this is the account's first method — the 8 recovery codes are returned **once**.
4. A pending address that is not confirmed within the code's lifetime is forgotten.
5. Nobody but the owner can put an address on an account: not an admin, not user creation, not an import. A request that names another username is refused.
6. One address may be the confirmed address of **one account per company** (open question O5). The check is inside the caller's own company only, so it cannot reveal whether an address exists in another company.

### 6.7 Changing or removing the address later

- **Change:** the person first proves the current second step with **a code emailed to the old address, or a code from the authenticator if the account has it**. Then the new address is confirmed by its own code. The old address stays the active one until the new one is confirmed. A recovery code alone is **not** enough to change the address (proposal: a found recovery sheet must not be able to move the second step to a new mailbox). After the change a short notice — no code, no link — goes to the **old** address.
- **Old mailbox lost and no authenticator:** the person signs in with a recovery code if they have one (that gets them working), and an admin resets their two-step (§6.8) so they can set up again with the new address. That is the only other way to change the address.
- **Remove (turn the email method off):** needs a current code from either method; deletes the address from the record; refused when it is the last method of a required account.
- **Authenticator on / off, new recovery codes:** as today, except that the current code may come from either method.

### 6.8 Recovery, slow email, lost mailbox

In the order a person meets them:

1. **Email is slow** — the screen says so after 20 s and offers "Send again" when the wait ends (`sign-in.md` §2). The code is valid for 10 minutes and the sign-in step does not expire under it (§6.9).
2. **The account also has the authenticator** — use it.
3. **Recovery code** — one of the 8, each works once. After signing in with one the person is told how many are left. At 2 or fewer left the Account / `/me` screen shows a reminder to make new ones.
4. **Admin reset of two-step (N20, new)** — a true admin of the same company clears the person's methods, address, pending address and recovery codes. The admin must type **their own** current code. The person's sessions end (§6.9) and their next sign-in lands on set-up. Refused in a sandbox company. Refused on oneself (an admin uses their own Account screen).
5. **Admin reset of the password (exists)** — `POST /api/users/pw`. Not by email, ever (decision e).
6. **The company's only admin is locked out** — the platform owner resets that admin's two-step from the platform console (new; audit entry on both sides). There is no other way in.
7. **Mail is down for everyone** — recovery codes and authenticators keep working. If it lasts, Ofir turns the wider requirement off (§10): un-enrolled managers and cs stop being held; an email-only account still needs a recovery code or an admin reset, after which — with the switch off — it signs in with a password until the switch is back on.

What the warehouse is told about this is in §9.4.

### 6.9 Session rules

- **The sign-in step and the code.** The pending step lives **10 minutes** from the correct password (today: 5). Each successful "send code" moves its end to that code's expiry, with a hard stop **20 minutes** after the password **(proposals)**. A code that is still valid is therefore never refused because "the step expired".
- **The session cookie never carries the code or the address.** The pending step holds the username and times only, as today.
- **SEC-10 — the reset half is in scope; the logout half is deferred.**
  - *In scope:* when an admin resets a person's password, when an admin or the platform owner resets a person's two-step, when a person turns a method on or off or changes their address, and when a person makes new recovery codes — **every session issued to that person before that moment stops working at its next request** (the session making the change is kept). Reason: resets are this feature's recovery path. A reset that leaves a stolen 7-day cookie working recovers nothing, and SEC-10's proposed mechanism (a per-user session version, checked where `_session_revocation` already re-reads the user record on every request) is small. The existing strict-xfail `test_sec10_password_reset_revokes_old_sessions` must pass with its marker removed.
  - *Deferred to SEC-10's own PR (with N5, native sign-out):* a cookie copied before `/logout` still working afterwards. Reason: ending "this one session" needs a per-session identity on the server; bumping the per-user version at logout would instead sign the person out of every device, which on a shared floor (station + phone) is a behaviour change nobody has asked for. It does not block the emailed code.
- **Live sessions on the day the requirement widens.** A required, un-enrolled account that is already signed in is held on the set-up screen **at its next request**, not only at its next sign-in (proposal; open question O3). Otherwise a session opened the day before stays unprotected for up to 7 days. This is why the switch is flipped outside packing hours.
- **Live sessions on the day SEC-2 lands.** A session that was opened by a badge and belongs to a required account ends at its next request, and the person signs in with password + code (§9.3).

### 6.10 Audit log

One entry each, with actor, target account, company, time and network address as the audit log already records them (`alog` — not read). **Never the code. The address only masked** (`m•••@n•••.com`).

| Event | Entry |
|---|---|
| Code emailed | `twofa.email.sent` — purpose (sign-in / set-up / change / action), masked address |
| Email could not be sent | `twofa.email.send_failed` — purpose, transport error class (no address, no body) |
| Address confirmed (method on) | `twofa.email.enabled` |
| Address changed | `twofa.email.changed` — old and new, both masked |
| Email method turned off | `twofa.email.disabled` |
| Authenticator on / off | `twofa.totp.enabled`, `twofa.totp.disabled` (not logged today in the range read) |
| New recovery codes | `twofa.recovery.regenerated` |
| Signed in with a recovery code | `twofa.recovery.used` — codes left |
| Second step locked by a limit | `twofa.locked` — which limit |
| Send limit reached | `twofa.email.send_limited` — which limit |
| Admin reset someone's two-step | `twofa.reset` — actor, target |
| Platform owner reset an admin's two-step | `twofa.reset.platform` — in the platform's log and in the company's |
| Requirement switched on / off | `twofa.policy` — old value, new value, by whom |
| Sessions ended by a reset | part of the reset's own entry |

Sign-in sends happen before a session exists; the entry must still land in the log of the company on the staff record.

## 7. Server contract (what the web page and the native screen call)

Contract level only: paths, what goes in, what comes back. Field names are proposals for the architect; **the existing fields the desktop sign-in page reads today (`ok`, `twofa`, `role`, `must_setup_2fa`, `used_recovery`, `expired`, `error`) keep their meaning** — everything new is added beside them. Every POST needs the `X-CSRF-Token` header as today (`app.py:3878-3887`); the app gets the token from `/api/mobile/session`.

Every failure answer carries a stable `error_code` beside the human `error`, so the app can show its own English or Spanish text.

### 7.1 `POST /api/login` — password (exists; answer extended)

| Case | Answer |
|---|---|
| Wrong username or password; suspended company; throttled | as today |
| Correct, sandbox company | signed in. Never `twofa`, never `must_setup_2fa` |
| Correct, account enrolled | `ok, twofa: true` **+** `methods` (any of `email`, `totp`), `email_masked` (only if email is on), `recovery: true`, `step_expires_in` (seconds). **Nothing is emailed by this call** |
| Correct, required and not enrolled | signed in with `must_setup_2fa: true` (as today for admins) |
| Correct, not required, not enrolled | signed in |

### 7.2 `POST /api/login/2fa/send` — email the sign-in code (new)

No body. Valid only inside a live pending step for an account whose email method is on.

| Case | Answer |
|---|---|
| Sent | `ok, email_masked, code_expires_in: 600, resend_in: 30 or 60, sends_left, step_expires_in` |
| Asked again before the wait ended | 429, `error_code: wait`, `retry_in` |
| A send limit reached | 429, `error_code: send_limit`, `retry_in`, and which other methods the account has |
| Mail could not be handed over in time | `ok: false, error_code: send_failed` — within **10 s (proposal)**; the request must not hold a worker for the transports' full waits |
| Email method not on for this account, or email not available on this server | `ok: false, error_code: email_unavailable` |
| No pending step / step expired | 401, `expired: true` (as today) |
| Sandbox account | cannot occur (no pending step exists); if forced, refused and nothing is sent |

### 7.3 `POST /api/login/2fa` — check the answer (exists; extended)

Body: `code`, and optionally `method` (`email`, `totp`, `recovery`). Without `method` the server tries what the account has, so today's desktop page keeps working.

| Case | Answer |
|---|---|
| Correct | signed in: `ok, role, used_recovery, recovery_left` |
| Wrong | `ok: false, error_code: wrong_code` (+ `tries_left` for an emailed code) |
| Emailed code past its lifetime, already used, cancelled by a newer one, or out of tries | `ok: false, error_code: expired_code` — **distinct from wrong** |
| A checking limit reached | 429, `error_code: too_many_tries`, `retry_in` |
| Step expired | 401, `expired: true` |

### 7.4 Set-up and management (signed in; all under `/api/2fa/`, which the set-up hold already lets through)

Allowed for an account that is required or already enrolled; refused (403) for others and for any sandbox account (`error_code: sandbox`).

| Call | In | Out |
|---|---|---|
| `GET /api/2fa/status` (exists; extended) | — | `required, must_setup, methods: {email: {on, address_masked}, totp: {on}}, email_available, recovery_left, can_disable: {email, totp}` |
| `POST /api/2fa/email/start` (new) | `email`; when the account is already enrolled also `code` (+ `method`) proving the current second step (§6.7) | as §7.2 "Sent", plus `error_code: bad_address` or `address_in_use` |
| `POST /api/2fa/email/confirm` (new) | `code` | `ok`; `recovery_codes` (8, once) when this was the first method; the session's `must_setup_2fa` is cleared |
| `POST /api/2fa/email/disable` (new) | `code` (+ `method`) | `ok`, or `error_code: last_method` |
| `POST /api/2fa/setup`, `/enable` (exist) | as today | as today; now also for manager and cs by rule, not through the manager→admin shortcut |
| `POST /api/2fa/disable`, `/recovery` (exist) | `code` (+ `method`) — a current code from either method | as today; `/disable` answers `last_method` for a required account whose only method it is (today it turns 2FA off and re-flags set-up) |

A full, unmasked address is returned only by `email/start`, to the session that just typed it.

### 7.5 `POST /api/2fa/challenge` — "email me a code" while signed in (new)

For the screens that need a current code from a signed-in person who uses email: turning a method off, new recovery codes, changing the address, deleting the account (SEC-7). Body: `purpose`. Sends an action code to the confirmed address; answers as §7.2. The code is accepted only by the call matching its purpose.

### 7.6 Admin and platform actions

| Call | Who | In | Out |
|---|---|---|---|
| `POST /api/users/2fa/reset` (new) | true admin, same company, not on oneself | `username`, the admin's own current `code` (+ `method`) | `ok`; target's methods, address, pending address and recovery codes cleared; target's sessions ended. `error_code: sandbox` in a sandbox company |
| Users list (exists, not read) | true admin | — | per user: `twofa_required`, `twofa_methods`, `last_password_login` — never the address in full |
| Platform console: reset an admin's two-step; set the requirement switch | platform owner | — | — (the console was not read; the architect places these) |

### 7.7 What this spec needs from `/api/mobile/session` (N3, N4)

Reachable while the set-up hold is active, and carrying: `must_setup_2fa`; `twofa: {required, methods, email_masked}`; `sandbox`. Without N4 the app gets 403 instead of a session when a manager must set up, and cannot show the native set-up screen.

## 8. The demo (sandbox) company — reference only

Designed by the architect in the sandbox document. From this spec's side, with the company's `sandbox` flag set:

- no account is ever required to set up, ever asked for a code, or ever held on set-up;
- no code email is ever sent, whatever is called — decided from the company on the **staff record**, because at sign-in no session exists yet (N17);
- every set-up, change and reset call in §7.4–7.6 is refused, so one reviewer cannot change the next reviewer's sign-in (security requirement 6).

### 9.3 A manager who signs in by badge today — day by day

- **Before step 1 (the briefing).** Told: "Soon your account will sign in with a password and a code sent to your email. Your badge will stop working for your account on a date we will announce. Make sure you know your password — if you don't, ask your admin for a new one this week. Have an email inbox you can open on your phone."
- **Day of step 1.** Scans the badge at the station: signed in exactly as yesterday. Nothing is asked. If they want, they open their profile and set up email now.
- **Day of step 3.** Scans the badge: **still signed in** — but lands on "Protect your account" and cannot do anything else until set-up is done (on a station: the `/me` set-up; in the app: the native screen). They type their email address, read the code on their phone, type it, save the recovery codes. About a minute, once. From then until step 5 the badge keeps working as before, and a line on their home screen and profile says: "From {date} this account signs in with a password. Your badge will stop working for this account." They are asked to sign in once with the password before that date, so that a forgotten password is found now and not on the day.
  - If they were already signed in when the switch was flipped, the same set-up screen appears at their next click.
  - If their inbox cannot be reached on the floor: they choose the authenticator app instead, or the admin postpones by leaving them on the readiness list — step 5 waits for them.
- **Between step 3 and step 5.** The admin's Users page lists who is ready. A manager who has not set up, or has not yet signed in with a password, holds step 5 back.
- **Day of step 5.** Scans the badge: "This account signs in with a password." The password form opens; nothing is filled in from the badge. They type username and password, tap "Send code", read the code on their phone, type it: signed in. A session already open from a badge ends at the next click with "Sign in again." Their workers' badges work as before.
- **If something is wrong that day:** a recovery code signs them in; or the admin resets their password or their two-step from the Users page (§6.8). The admin is reachable that day by plan (§9.4).

### 9.4 What the warehouse must be told before each deploy

Before step 1 (managers, cs, admins — in English and Spanish, by the manager's usual channel):

1. What changes and for whom: admin, manager, cs. **Workers and hosts: nothing changes; badges keep working.**
2. You will need: your password (ask the admin for a new one now if you never knew it), and an email inbox you can open on your own phone, or an authenticator app.
3. Use **your own** mailbox — not a shared one, and not one whose password is the same as your Live Ops Hub password.
4. The email comes from {sender — Q9}, subject "Your Live Ops Hub sign-in code". Check junk the first time and mark it "not junk". It never contains a link; never give the code to anyone.
5. Save the recovery codes somewhere that is not that mailbox.
6. If you are stuck: recovery code → ask the admin (reset on the Users page). There is no "forgot password" link.

Before step 3: the date and hour; "the first sign-in after it takes one extra minute".

Before step 5: the date and hour, at least **three working days** ahead (proposal); the names still not ready, to the admin; an admin is on site or reachable for the first shift after it; keyboards are available where managers and cs sign in (open question O2 — floor stations were built for badge-only use).

### 9.5 Switching it off (no deploy)

- **The requirement switch** is a platform setting changed from the platform console by the platform owner, read by every worker on each sign-in and each held request (not a process-start environment value — changing a Railway variable restarts the service, and a value cached per worker would differ between workers). Values: "admins by primary role" (today's rule) and "admin, manager, cs by effective roles".
- Switching back: required-but-not-enrolled managers, cs and extra-role admins are released from the set-up hold at their next request and sign in as before step 3. Accounts that enrolled keep their second step (enrolled accounts are always asked). Nothing is deleted.
- **A second switch turns the email method off** (not offered, no sends) if the sender is blocked or abused. Accounts whose only method is email then use a recovery code or an admin reset; with the requirement switch also off, a reset account signs in by password.
- **SEC-2 is rolled back by reverting its PR** (a deploy). It needs no switch of its own, because step 4 guarantees nobody depends on a badge by then; if the architect prefers a switch there too, it must default to "badge for floor roles only".
- Rolling back does not restore removed badges; an admin re-issues them.

## 10. Acceptance criteria

Each line is a statement qa can check. "Required account" = effective roles include admin, manager or cs, in a non-sandbox company, with the requirement switch on. Tests replace the mail transport with a recorder; no test sends real email.

### A. Who is asked

- **A1** With the switch on, an account with primary role manager and no method signs in with its password and is flagged `must_setup_2fa`; the same for primary role cs; the same for `role: worker` with `extra_roles: ["admin"]`, `["manager"]` or `["cs"]`.
- **A2** With the switch on, a worker and a host with no such extra role sign in with no flag and no second step.
- **A3** With the switch off, A1's manager, cs and extra-role accounts sign in with no flag; a primary-role admin is flagged exactly as before this change.
- **A4** An enrolled account is asked for the second step with the switch on and with it off.
- **A5** The strict-xfail `test_sec1_extra_role_admin_must_enroll_2fa` passes with its marker removed (switch on).
- **A6** A held account gets 403 `need_2fa_setup` from an ordinary `/api/` route and 200 from `/api/2fa/status`, `/api/2fa/email/start`, `/api/2fa/setup`, `/api/mobile/session`, `/logout`.
- **A7** A required, un-enrolled account whose session was created before the switch was turned on is held at its next request, without signing in again.
- **A8** `GET /api/2fa/status` answers 200 for admin, manager and cs; a worker with no required role gets 403 from every set-up call.

### B. Enrolment by email

- **B1** `email/start` with a well-formed address records one email to that address in the recorder and returns `resend_in`, `code_expires_in`, `sends_left`.
- **B2** Before `email/confirm` succeeds, the user record has no confirmed address, the account is still held, and a sign-in for it offers no email method.
- **B3** `email/confirm` with the right code stores the address, turns the method on, clears the hold in the same session, and returns exactly 8 recovery codes when it is the first method and none when the authenticator was already on.
- **B4** `email/confirm` with a wrong code answers `wrong_code` and changes nothing; with a code older than its lifetime, `expired_code`.
- **B5** A malformed address (no `@`, spaces, longer than 254 characters, a line break) answers `bad_address` and the recorder stays empty.
- **B6** A code sent to address X is refused when the pending address has since been changed to Y.
- **B7** An admin cannot set, see in full or change another user's address through any route; user creation with an `email` field in the body stores no address.
- **B8** The same address cannot be confirmed on a second account of the same company (`address_in_use`); the answer for an address used only in another company is indistinguishable from a normal send.
- **B9** After set-up, no answer except `email/start` to the typing session contains the full address; `status`, `/api/login` and `/api/mobile/session` contain it masked.

### C. Changing and removing

- **C1** `email/start` on an enrolled account without a valid current code is refused and sends nothing.
- **C2** With a code emailed to the old address (§7.5), or with an authenticator code, a new address can be started; the old address remains the one sign-in codes go to until the new one is confirmed.
- **C3** A recovery code is refused as the proof for changing the address.
- **C4** After a confirmed change, the recorder holds one notice to the old address containing no code and not the new address.
- **C5** `email/disable` with a current code removes the address from the user record; for a required account whose only method is email it answers `last_method` and changes nothing.
- **C6** `/api/2fa/disable` on a required account whose only method is the authenticator answers `last_method`; with email also on, it turns the authenticator off and the account is not held.
- **C7** `/api/2fa/recovery` and `/api/2fa/disable` accept a current emailed action code as well as an authenticator code; a sign-in code is refused there.
- **C8** After new recovery codes are made, every old one is refused.

### D. Sign-in, web and app

- **D1** `POST /api/login` for an enrolled account returns `twofa: true` with `methods` and, when email is on, `email_masked`; the recorder is still empty (no email is sent by the password step).
- **D2** `POST /api/login/2fa/send` inside the pending step records one email and returns the fields in §7.2; outside a pending step it answers 401.
- **D3** `POST /api/login/2fa` with that code signs in and returns `role`; the same code sent again is refused.
- **D4** A wrong code answers `wrong_code`; a code past its lifetime answers `expired_code`; the two are different values.
- **D5** An account with both methods signs in with either; an account with only the authenticator gets `email_unavailable` from `send` and no email is recorded.
- **D6** A recovery code signs in, is refused the second time, and the answer carries `used_recovery: true` and `recovery_left`.
- **D7** The desktop sign-in page's existing call — `POST /api/login/2fa` with only `code` — still signs in an authenticator account (existing tests for the admin flow stay green, unmodified).
- **D8** A code sent 9 minutes after the password is accepted 9 minutes later (the step did not expire under it); 20 minutes after the password, the step answers 401 `expired` whatever was sent.
- **D9** The whole flow D1–D3 passes using only JSON calls and the CSRF header from `/api/mobile/session`, with no HTML page fetched (the native screen's path).
- **D10** Browser check on the desktop sign-in page: after the password, an email-only account sees the masked address and a "Send code" control; the wait is visible; a wrong and an expired code show different messages. (Page not read; product-designer's UX section defines the layout.)
- **D11** A held manager on the web is redirected to `/me?setup2fa=1` and can complete email set-up there without an authenticator; a held cs user can too.

### E. The code itself

- **E1** Codes are 6 decimal digits; over 1,000 generated codes no digit position is constant and the generator is the system's secure random source (code review + test).
- **E2** A code is refused 10 minutes and 1 second after sending.
- **E3** Sending a second code makes the first one answer `expired_code`.
- **E4** After 5 wrong tries the correct code answers `expired_code`.
- **E5** A set-up code is refused at sign-in; a sign-in code is refused at set-up and at an action; a code for account A is refused for account B.
- **E6** **Several workers:** with the test app instantiated twice over the same data directory (or two processes), a code sent through one is accepted through the other; a wrong try through one counts against the limit seen by the other; a send through one starts the wait seen by the other.
- **E7** No module-level or process-memory structure holds a code, a pending address, or a send or try counter (code review; the fallback in `_rate_ok` that counts in memory is not used for these).
- **E8** The stored form of a code is not the code and cannot be matched by hashing the one million candidates without the server's secret (code review).
- **E9** With output captured during set-up, sign-in, a failed send and a throttle hit — in production mode and in staging mode — the code appears nowhere in stdout, stderr, the audit log, the subject, any response body, or the session cookie's decoded content; the full address appears in none of the logs.

### F. Limits (values from §6.4–6.5, read from one place so they can change)

- **F1** A second send within 30 s answers 429 `wait` with `retry_in`; a third within 60 s of the second likewise; nothing is recorded for either.
- **F2** The 6th send for one account within an hour answers 429 `send_limit`; the 11th within 24 hours likewise — whatever the purpose and whatever network it came from.
- **F3** The 6th send to one address within an hour is refused even when asked from different accounts.
- **F4** The 31st send from one network address within an hour is refused; a different address is unaffected.
- **F5** 10 wrong second-step answers for one account from 10 different network addresses within 15 minutes → the 11th answers 429 `too_many_tries`, and so does a **correct** code until 15 minutes pass. (The 2FA half of `test_sec11_login_lockout_is_per_account`.)
- **F6** Sending a new code does not reset F5's count; a correct answer does.
- **F7** 30 wrong answers in 24 hours lock the second step until 24 hours pass or an admin reset; the lock writes `twofa.locked`.
- **F8** None of F1–F7 can be triggered for an account without first sending its correct password (a request with only the username changes no counter of §6.4–6.5).
- **F9** All counters survive a worker restart and are shared between workers (as E6).

### G. Mail behaviour

- **G1** With no mail transport configured, `status` returns `email_available: false`, `email/start` and `login/2fa/send` answer `email_unavailable`, and the set-up screen offers only the authenticator.
- **G2** In staging mode the same as G1 — the server does not answer "sent" for an email it suppressed.
- **G3** With the transport replaced by one that never answers, `send` returns `send_failed` within 10 s and the worker is free.
- **G4** The recorded sign-in email has exactly the subject and both language blocks of §6.11, contains the code once per language block, contains no `http`, no `www.`, no `<a`, no `<img`, and has a plain-text part.
- **G5** The subject contains no digit sequence of 6.
- **G6** The address is used by no other feature: no other code path reads the confirmed address (code review), and deleting the account removes it from the user record.

### H. Recovery and resets

- **H1** `POST /api/users/2fa/reset` by a true admin of the same company with the admin's own valid code clears the target's methods, address, pending address and recovery codes; the target's next sign-in (switch on) is held on set-up.
- **H2** The same call is refused: without the admin's code; with a wrong one; from a manager; from a cs user; for a user of another company (404, same answer as "not found"); on the caller's own account; in a sandbox company.
- **H3** The platform owner can reset the two-step of an admin of any non-sandbox company; both logs get an entry.
- **H4** After a reset, the target's old recovery codes are refused.
- **H5** No route on the server changes a password in exchange for an emailed code or link; the sign-in page and the app have no "forgot password" control (code review + browser check).
- **H6** After a recovery-code sign-in, `status` reports the remaining count.

### I. Sessions (SEC-10, reset half)

- **I1** A session cookie captured before an admin resets that user's **password** is refused at its next request (401 `session_revoked` for `/api/`, redirect for pages). `test_sec10_password_reset_revokes_old_sessions` passes with its marker removed.
- **I2** The same after an admin or platform two-step reset.
- **I3** After a person turns a method on or off, changes the address or makes new recovery codes, their **other** sessions are refused and the session that made the change keeps working.
- **I4** A session of a different user of the same company is unaffected by I1–I3.
- **I5** Explicitly **not** required here: a cookie copied before `/logout` being refused afterwards (stays a strict xfail under SEC-10).

### J. Audit log

- **J1** Each event in §6.10 writes exactly one entry with the listed name, the actor and the target.
- **J2** No audit entry contains a code or a full address.
- **J3** A sign-in send (no session yet) is written to the log of the company on the staff record, and to no other company's.
- **J4** A manager cannot read the audit log (unchanged: `/api/audit-log` is on the manager block list).

### K. Sandbox (checked again by the sandbox spec's own criteria)

- **K1** In a company flagged sandbox, a manager and a worker sign in with a password only, with the switch on and off; `twofa` and `must_setup_2fa` are never true.
- **K2** Every call in §7.2, §7.4, §7.5 and §7.6 from or about a sandbox account leaves the mail recorder empty and changes no user record.
- **K3** A `twofa_exempt: true` field on a user of a non-sandbox company does not exempt them.

### L. Switches and roll-out

- **L1** Turning the requirement switch on and off needs no deploy and no restart: with two app instances over the same data, a change made through one is in effect on the other at its next request.
- **L2** Only the platform owner can change either switch; an admin of a company gets 403. Each change writes `twofa.policy`.
- **L3** With the email switch off: no send is recorded by any call; an account with both methods signs in with the authenticator; an email-only account signs in with a recovery code.
- **L4** Step 1 state (both PRs merged, requirement switch off): the full existing test suite passes unmodified except for tests whose xfail markers this spec removes; a manager's badge sign-in and password sign-in behave exactly as before.
- **L5** Step 3 state (switch on, SEC-2 not merged): a required, un-enrolled account that signs in **by badge** gets a session flagged `must_setup_2fa` and is held (today the badge path never sets the flag); an enrolled one gets a normal session.
- **L6** The Users list returns, for every user of the company, whether two-step is required, which methods are on, and whether a password sign-in happened since the switch was turned on; it is admin-only.
- **L7** SEC-2's PR description names the readiness check of §9.1 step 4 and the `PROVEN.md` line of §9.1; qa refuses it without both. (Process criterion.)
- **L8** After SEC-2 (its own tests): `test_sec2_badge_login_never_yields_admin` passes with its marker removed; a worker's badge still signs in; the badge of an account with a required role answers "This account signs in with a password" and creates no session.

### M. Invariants touched (qa confirms each)

- Several gunicorn workers: E6, E7, F9, L1.
- Company isolation: B8, H2, J3; no answer reveals whether a username or address exists in another company.
- Roles enforced on the server: A8, H2, L2.
- Output escaped: a typed address shown on `/me`, the Users page or in an error is HTML-escaped (an address containing `<script>` is rejected by B5 and, if stored by any path, rendered inert).
- Outbound calls have timeouts: G3.
- Warehouse progress, stock and money actions: not touched.

## 11. External guidance and limits checked (read online 2026-11-11)

| Source | What it says, in short | What this spec does with it |
|---|---|---|
| NIST SP 800-63B-4, "Authenticators" — `pages.nist.gov/800-63-4/sp800-63b/authenticators` | Federal guidance rules email out as an out-of-band authenticator ("Email SHALL NOT be used for out-of-band authentication"), naming mailbox access by password alone, interception and rerouting as the reasons; codes that only validate an address are not covered by that ban. It also sets a 10-minute limit for completing an out-of-band step, single use, at least six decimal digits, rate limiting for short secrets with an upper bound of 100 consecutive failures, and says a new secret must not reset the failure count. | The method is Ofir's decision and is not reopened. The weakness is recorded honestly: **an emailed code is only as strong as the person's mailbox.** Mitigations in this spec: no password reset through the same mailbox (decision e), own mailbox with a different password (§9.4), authenticator offered beside it, tight limits (§6.3–6.5 follow the 10-minute, six-digit, single-use and no-reset-on-resend rules). | OWASP Multifactor Authentication Cheat Sheet — `cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html` | Lists email for completeness and notes it depends wholly on the mailbox's own security and gives nothing if the mailbox falls first; says a way back in is needed but must not become a bypass; suggests single-use recovery codes handed out at set-up. | Recovery codes at first set-up (§6.6); resets need the admin's own code and are audited (§6.8); recovery code cannot move the address (§6.7). |
| Resend, API rate limit — `resend.com/docs/api-reference/rate-limit` | Default ceiling of 10 requests per second per team; over it the API answers 429 with `retry-after`. | Far above our volume. A 429 from the mail service must surface as `send_failed`, not as a hung request (G3). |

If it is Resend's free plan, code emails share 100 per day with new-hire invites — enough for one warehouse, not for outside sellers. Ofir confirms with Q9 (§13). |

Not checked: whether iOS offers a code from Mail above the keyboard for the app's code field; deliverability of any sender; Apple's review position on email codes. Nothing is asserted about them.

## 13. Metrics to watch after each step

- Code emails sent per day, by purpose; `send_failed` and `send_limited` counts (alert: any `send_failed` streak of 3).

- Share of second steps completed by email / authenticator / recovery code; recovery codes used per week.
- Admin two-step resets and password resets per week.
- `twofa.locked` events.
- Required accounts not yet enrolled; required accounts still signing in by badge (must reach zero before step 5).
- Floor health on the mornings after steps 3 and 5: first-order-picked time and orders packed by 10 am against the previous week — a locked-out manager shows up there.
